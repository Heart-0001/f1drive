
################ gamepad ABXY

== summary
I remapped the controller in js/gamepad.js to the v6.1 layout, and it is verified both in the unit suite and in the real game. Only button indices changed: state.boost, state.pressed.{reset,line,menu,recentre,limiter,compound}, mergeInput, rumble, onChange, active and the 500 ms edge resync work exactly as before (a diff of the code against the old copy shows only the mapping lines changed). The header comment now has the full table.

New standard mapping: A[0] or RB[5] held = battery; B[1] or LB[4] = limiter (edge); X[2] = next compound (edge); Y[3] = reset (edge); View/Back[8] = racing line (edge); Menu/Start[9] = menu; RS click[11] = recentre. When two buttons share a function they are OR-ed, so pressing the second while the first is held is not a new press. Triggers, sticks and D-pad are unchanged. The raw (non-standard) layout is mapped the same way by name: A0 / RB5 battery, B1 / LB4 limiter, X2 compound, Y3 reset, Back6 line, Start7 menu, RS10 recentre.

devtests/gamepad-test/gamepad.test.js is updated and now passes 25/25 (exit 0). It includes a new table test that presses every standard button (0-16) alone and every raw button (0-10) alone and checks what each one does. To check the tests catch mistakes, I ran them against the old gamepad.js and against two broken copies (Back mapped wrongly on the raw layout, B not combined with LB); all three fail.

I also added devtests/gamepad-test/game-map.js. It drives the real index.html + main.js in one offscreen window that is muted through devtests/electron-userdata.js (SOUND was never set), using a fake controller. Result: ALL PASS 11/11 on Monza with the 2025 standard car. It confirms A and RB deploy the battery, B does not, B and LB toggle the limiter, X cycles the compound (M -> H -> S) and View does not, View toggles the racing line and X does not, Y resets the car and A does not, Menu opens and resumes, RS click recentres, and there are no console errors.

Several existing harnesses press the old indices and now fail (exact lines are under openIssues). I checked that the fixes work by running edited copies in my scratchpad; no project file outside my folders was changed:
- gp-smoke pad part: unchanged 22/25 (exit 1) -> edited copy 25/25.
- v6-smoke pad part: unchanged 3/6 (exit 1) -> edited copy 6/6.

################ seasons ERS data

== summary
Every car 2011..2026 now has its own battery from tools/ers-data.json, and each car's lap-time target still holds when it is driven with the battery deployed.

What the data now says:
- **Batteries:** deploy, harvest and store from tools/ers-data.json replace perf.ersPower, perf.ersHarvest and a new perf.ersStore. They are not multiplied on top of the js/cars-data.js values.
- **Cars without KERS:** five cars have hasErs false, so their CarSpec has ers: null: 2011-lotus-racing, 2011-hrt, 2011-virgin, 2012-hrt and 2012-marussia. All of 2010 has no battery either. Every 2013 car has KERS.
- **Lap times unchanged:** every season's standard car and era physics are byte-identical to before, so calibrate.mjs was not re-run. The only exception is a display value: the 2010 standard car's battery bar went from 50 to 0, on purpose (that season has no battery). Of the 168 cars in 2011..2026, 111 changed their multipliers: the 100 cars of 2011..2025 whose battery differs from the standard one, plus all 11 cars of 2026. The other 57, and all of 2010, have exactly the same multipliers as before.

How the lap time is kept on target: the per-car level solve uses the racing-line speed model, which has no battery. So a new script, devtests/seasons-calib/ers-effect.mjs, measures each battery's effect by driving. It fits each season's standard car with each distinct battery of that season (49 in total), drives all 40 circuits with E held, and writes devtests/seasons-calib/ers-effect.json. tools/build-cars.mjs then solves the chassis level so that speed-model delta + battery effect = target. A strong battery therefore gets a weaker chassis and a car without KERS a stronger one, with the same lap time and a different character.

Measured battery effects (mean over the 40 circuits, against the season's standard car; positive = slower):
- **No KERS:** +0.555 % in 2011, +0.538 % in 2012.
- **2011 Red Bull** (deploy 0.92, harvest 0.92): +0.05 %.
- **Mercedes 2014–16** (1.08 / 1.12): −0.17 to −0.19 %.
- **Renault 2014–15** (0.88 / 0.92): +0.25 to +0.26 %.
- **Honda 2015** (0.84 / 0.76): +0.39 %.
- **Honda 2021** (1.12 / 1.12): −0.19 %.
- **2026:** Aston Martin (0.88 / 0.88) +0.16 %; Mercedes (1.04 / 1.0502) −0.05 %; the other 2026 cars −0.03 to +0.04 %.

Examples of the chassis level change (%):
- **2011:** Team Lotus −0.72 → +0.22; HRT −1.52 → −0.61.
- **2014:** Mercedes +0.67 → +0.40; Red Bull +0.50 → +0.88.
- **2015:** McLaren −0.21 → +0.37.
- **2021:** Red Bull +0.76 → +0.44.
- **2026** (had no level before): Aston Martin +0.27; Mercedes −0.08.

No multiplier reaches a range edge: chassis and engine multipliers stay within 0.955..1.030.

2026 keeps the js/cars-data.js power, drag and chassis multipliers plus one common level L. Its target is the speed-model delta those multipliers already gave (the cars-data pace was derived without the battery). The 2026 order is unchanged and now matches the data target exactly in the driven check (rank correlation 1.000, was 0.991).

Battery bar: gain lowered from 13 to 3.5, and 0 for any car without a battery. Examples: Honda 2015 6, Aston Martin 2026 16, Renault 2014 20, Ferrari 2014 50, Mercedes 2014–16 80, Honda 2021 84.

js/cars.js now allows ers null per car (never for the standard car), clamps the battery multipliers to 0.75..1.15 (store 0.9..1.1) with every other range unchanged, adds F1.cars.ersNote(id) (a Map lookup), and still uses Map-only lookups.

docs/seasons-data.md has a new battery section with the effect table and level changes, an updated drive-check table, decisions and limits.

Defaults I chose, all recorded in docs/seasons-data.md:
- **2026 Mercedes harvest cut to 1.0502 (data says 1.08).** The 2026 era harvest (2190 W/kg) already sits at js/car.js's ceiling / 1.05; 1.08 would push it over the ceiling and car.js would silently drop it to the reference's 230 W/kg. Widening this would mean changing the 2026 standard car and re-running the 22-minute calibration. It is still the highest harvest of 2026, and the build prints a NOTE about it.
- **js/cars.js clamps an out-of-range battery value to the edge** instead of falling back to the reference value, so a 2026 car can never lose 90 % of its harvest.
- **The 2010 standard car's battery bar is now 0** (it was 50), consistent with every other car without a battery.

Known side effect: when E is not pressed, the battery differences disappear but the chassis differences remain. So within a season, cars without KERS or with a weak battery become relatively faster: check-drive.js --teams (which never presses E) shows 2011 Team Lotus 0.12 % ahead of the standard car. This is the intended character change, since targets are defined with E.

== apiNotes
 - UI: show the battery note. Each car row in js/seasons-data.js has ersNote, a one-line Traditional Chinese string ('' when there is none; 128 of 168 cars have one, at most 43 characters). The CarSpec does NOT carry it, so in the car card the UI should call F1.cars.ersNote(spec.id), which returns '' for unknown or hostile ids. Example: 2015-mclaren -> 'MGU-H 回收不足：跑到半圈電能就用光'.
 - UI: no-battery cars. CarSpec.ers === null now also for 2011-lotus-racing, 2011-hrt, 2011-virgin, 2012-hrt and 2012-marussia (as for all of 2010), and their ratings.ers is 0. ui.js hasErs() already hides the battery bar for ers === null; the telemetry should hide the battery as it already does for 2010 (v6-smoke checks this for 2010).
 - Data shape added in js/seasons-data.js car rows: perf.ersStore (multiplier), hasErs (boolean), ersNote (string), est.ersPct (the battery's share of est.lapPct). est.lapPct now means the lap with the battery deployed, against the standard car also deploying.
 - Multiplier ranges: ersPower and ersHarvest 0.75..1.15, ersStore 0.9..1.1; all other multipliers still 0.95..1.05. The contract text in js/README-interfaces.md (perf comment '0.95..1.05', the F1.cars API list) is not mine to edit. It should add: the battery ranges, ersStore, hasErs / ersNote in the data, F1.cars.ersNote(id) -> string, 'ratings.ers 0 when ers is null', and per-car ers null for 2011-2012.
 - js/cars.js: hasErs false gives ers null except for the '<year>-standard' car, which always gets the era's battery. Only the value false removes a battery. A battery value (era x multiplier) outside js/car.js's 1/10..10 x reference window is now clamped to the edge, not replaced by the reference value; physics values still fall back to the reference as before.
 - Workflow: if tools/ers-data.json changes, re-run `node devtests/seasons-calib/ers-effect.mjs` (about 3.5 min with the default 4 child processes) and then `node tools/build-cars.mjs`. The generator refuses a missing or stale ers-effect.json, or one lacking a battery some car uses. ers-effect.json is fingerprinted against calibration.json, so it must also be re-run after any calibrate.mjs run. calibrate.mjs is unchanged; its harvest ceiling still uses CFG.MAX = 1.05.
